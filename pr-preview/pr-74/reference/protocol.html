Protocol: the shape every model has

Every model in this crate is a labelled-step state machine: a state, a label for each kind of step, an initial predicate, and a relation saying which labelled steps are allowed. Each module spelled that differently (init/next, raft_init/raft_next, ray_init/ray_next, swim_init, actor_init, mb_init, composed_init), so nothing in the types said what a protocol is.

protocol::Protocol (src/protocol_t.rs, trusted) is that shape, written once: an associated Config, State and Step, an init, a step, and a provided next that is “some step”. Each model implements it at the bottom of its own model_t.rs. The agreement lemmas (src/protocol_v.rs, verified) pin each instance to the model it describes.

What this does not say

  • It is a shape, not a relationship. No theorem here relates two protocols. In particular the composed machine’s Protocol instance is written by hand; it is not derived from the ownership and Raymond instances. Deriving it is the generic composition tracked in #67.
  • There is no observable view. What a consumer of a protocol may read (a membership protocol’s peers, a log’s committed prefix) is defined alongside the first property that reads it, in the membership contract (#65).
  • No liveness for the other protocols. runs_of exists, but only the mailbox states a liveness theorem against it (P3). Giving the others one is separate work per protocol, and each needs its own fairness assumption.
  • Nothing about the services. The service code is plain Rust and does not implement Protocol; it calls the verified step functions, which the refinement rows in the per-protocol chapters tie to the models.

Composition

compose::Product<A, B, K> (src/compose_t.rs, trusted) is two protocols and the way they meet. Its state is both parts’ states and the coupling’s own (the glue); its steps are A moving alone, B moving alone, or a joint step that belongs to neither, defined by the coupling K: Coupling<A, B>. The coupling is the only place the two meet: a guard on a part’s step may read the other part and the glue, and the glue may change when a part moves, but a part never moves the other.

What composition does not say

  • The coupling may be wrong. A coupling too strong to be useful is safe vacuously. P4 is why a composition needs only its coupling proved; it is not a check that the coupling lets the interesting things happen. For the composed machine that check is its scenarios (composed::proofs::scenario). A new composition needs its own.
  • One instance so far. Coupling was written against the one composition the crate has, and it fits that one exactly (P6). Whether it fits the next (Raft with ownership, the mailbox with Host) is what building them will show; nothing here claims it already does.
  • The composed model is not rewritten. It stays hand-written and every theorem in its chapter stays stated against it. P6 is the bridge, not a replacement.
  • No liveness. Fairness does not compose by this argument; each composition that wants a liveness theorem states its own.
  • No services. This is the machine. How a composed service is assembled from two services is a separate question: the #[service] macro takes a trait, not a pair of them, so the composed service’s trait is still written out.
